# Grant Platform

Full documentation: [`docs/PROJECT.md`](docs/PROJECT.md). Secret values: the git-ignored `secrets.local.md` (never commit it). Build log: `work.md`.

A new grant-management web app built from the supplied applicant and admin dashboard/profile specifications.

## Current delivery

This is an explicitly labeled **interactive demo**, not a production financial service: grants, balances and cards are sample data. With Supabase configured, people sign in for real (Supabase Auth; `src/lib/auth.tsx`, `src/pages/auth.tsx`); admins land in `/admin`, applicants everywhere else. Without it (development only, `AUTH_MODE=demo`) the old preview identities and the User/Admin workspace switch come back, and that switch is **not authentication**. Do not add real customer information yet.

- Express 5 API at `/api`, managed on port 8080: `artifacts/api-server`
- Contract: `lib/api-spec/openapi.yaml`; generated hooks and validation: `lib/api-client-react`, `lib/api-zod`
- Drizzle sample schema: `lib/db/src/schema/demo-*.ts`
- Sample seeding: `artifacts/api-server/src/lib/demoSeed.ts`
- Workspace behavior/transactions: `artifacts/api-server/src/lib/demoWorkspace.ts`

- `pnpm run typecheck` for all libraries and apps

- **Schema changes are versioned migrations:** edit `lib/db/src/schema`, run `pnpm --filter @workspace/db run generate` (writes `lib/db/migrations/NNNN_*.sql`; review it), then `pnpm --filter @workspace/scripts run db:migrate`. It applies each migration once, on whichever DB the app uses, plus the Supabase-only SQL in `lib/db/supabase/migrations` when the target is Supabase. A new table also needs its `app_api_all` policy in a Supabase migration. `db run push` stays for throwaway local experiments only. `db:migrate -- --baseline` was used once on 2026-10-29 for the two DBs built with push.

Supabase TLS is **verified** against the pinned Supabase Root 2021 CA (`lib/db/src/supabaseCa.ts`, valid to 2031-04-26). Supabase is Postgres 17: back it up with a v17 `pg_dump` (see work.md, 2026-10-29).

## Backend and security boundaries

- Profile edits, tier/permission updates, account freezes, global freeze and sample balance top-ups persist in Postgres and create append-only application audit records.
- Money is stored in integer cents. Sample ledger changes and audit writes share a transaction, using row locks. Global freeze and individual account freeze block sample top-ups.
- **RLS:** every table has RLS on (schema `.enableRLS()`, migrations, and the dashboard's `ensure_rls` trigger). The only policies are `app_api_all` for the API role. `anon` and `authenticated` hold no grants on app tables, so Supabase's public Data API is refused outright. Default privileges keep that true for future tables.
- Every money movement is a row in `demo_ledger` (signed cents, linked to its request or application). Approving a deposit credits the deposit balance; approving a withdrawal debits the balance the applicant chose (grant, or deposit when an admin has opened it to that user); approving an application credits the grant balance. Every deposit and withdrawal request goes through an admin-made payment method (`demo_payment_methods`, Phase 10) and keeps a copy of it (`method_snapshot`). Approvals lock settings → profile → record, re-check freezes, balance and the user's KYC requirement, and write ledger + audit + notification in one transaction. Declines need a reason and move no money.
- `demo_audit`, `demo_ledger` and `demo_application_events` are append-only: triggers installed at boot (`demoSeed.ts`) refuse UPDATE/DELETE (TRUNCATE for test resets still works). The dashboard's "Audit log: Intact" checks those triggers exist.
- **API auth** (`artifacts/api-server/src/lib/auth.ts`): every route except `/healthz` verifies a Supabase access token. The token is ES256, checked against the project's JWKS for issuer, audience `authenticated` and expiry. No token or a bad one → 401. The role comes from `app_metadata.role` (only writable with the secret key): `admin`/`root` may use `/admin/*`, everyone else is an applicant and may use only `/applicant/*` (otherwise 403). An applicant's `demo_profiles` row (linked by `auth_user_id`) is created on their first request. `currentUserId()` / `currentAdmin()` read the verified identity; admin actions are recorded with the admin's email. `POST /api/auth/session` mirrors the token into the HttpOnly `gp_session` cookie, which authenticates **GET requests only** (images, downloads), so a cookie can never trigger a change.
- `AUTH_MODE=demo` keeps the old preview identities (Jane / Demo administrator) and is refused when `NODE_ENV=production`. Unset, the API uses Supabase whenever `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` are set (always in production) and falls back to demo only in development without them. The browser learns the mode and public keys from `GET /api/auth/config`.
- Frontend sign-in: supabase-js (pinned 2.117.3, **PKCE** flow; our emails link to `/auth/confirm?token_hash=…&type=…`, which calls `verifyOtp`, so no session tokens ever sit in a URL, links work on any device, and mail scanners can't use them up) supplies the bearer token through `setAuthTokenGetter`; `POST /api/auth/session` runs before the workspace renders and after each token refresh. Signing out or switching user clears the React Query cache; saved grants and setup progress in localStorage are kept per user. Supabase dashboard settings the app depends on: Site URL and Redirect URLs (the app origin plus `/reset-password`).
- **Sessions:** besides the signature, every token is re-checked with Supabase's `/auth/v1/user` (cached ≤ 60 s per token). Signed-out sessions, bans and removed admin rights take effect within a minute, and the role comes from that live answer. If Supabase can't be reached, the API answers 503 (the app shows "try again"), not 401. Changing or resetting a password signs out every other session.
- **Abuse limits and headers:** per-IP (600/min), per-account writes (60/min), uploads (20/10 min) and email-hook (120/min) limits in `lib/rateLimit.ts`, in memory by default (one server); with `RATE_LIMIT_REDIS_URL` the counts are shared through Redis (`lib/redisClient.ts`, own minimal client; if Redis is down each request is counted in memory instead, never refused). They're configurable with `RATE_LIMIT_*`; tests raise them. Behind nginx set `TRUST_PROXY=1`. The API sends nosniff, `X-Frame-Options: DENY`, `CSP default-src 'none'`, CORP same-origin, Permissions-Policy and HSTS (production), with JSON bodies capped at 100 kB. The production web build carries a strict Content-Security-Policy (`vite.config.ts`): scripts only from the site; network only to the site and `*.supabase.co`.
- **Settings → Sign-in & security** (`src/components/security.tsx`, applicant and admin Settings; hidden in demo mode): change password (the current one is re-checked with a fresh sign-in first, since Supabase doesn't ask for it), sign out of other devices (`scope: 'others'`) and sign out everywhere (`'global'`, with a confirmation). Revoked devices can't refresh; a device that's open keeps its access token until it expires (≤ 1 hour). Applicants switch their own email notifications (`PATCH /api/applicant/preferences`, audited); the other account settings stay admin-managed.
- **Email** goes only through Resend (`lib/email.ts`; templates in `lib/emailTemplates.ts`, every value HTML-escaped). Configured in **Admin → Settings → Email** (`lib/emailSettings.ts`): Resend key and hook secret encrypted with `SETTINGS_ENCRYPTION_KEY`, or when unset with a key file the API creates itself (`settings.key` next to `UPLOAD_DIR`, git-ignored, not in backups; `lib/secretBox.ts`) (write-only, hints only), sender, reply-to, support address, signature, health checks, test email. Saved values win over `RESEND_API_KEY` / `EMAIL_FROM` / `SEND_EMAIL_HOOK_SECRET`, which remain a fallback; without a key and sender, email is off. `email.ts`, `emailTemplates.ts` and `sendEmailHook.ts` never import the database: `emailSettings.ts` pushes settings into them (`setEmailRuntime`, `setEmailBranding`).
  - Supabase Auth emails: Supabase's **Send Email Hook** POSTs to `/api/hooks/supabase/send-email` (`lib/sendEmailHook.ts`, mounted before `express.json()` because the Standard Webhooks signature covers the raw body; 5-minute timestamp window; replays answered without resending; Resend idempotency keys). Needs `SEND_EMAIL_HOOK_SECRET` (the `v1,whsec_…` value from the dashboard) and a public HTTPS URL. For email changes Supabase's token fields are reversed: the current address gets `token_hash_new`.
  - In-app notifications are also emailed by an outbox worker (`lib/notificationMailer.ts`, every 15 s, `SKIP LOCKED`, up to 5 tries within 24 h, columns `demo_notifications.emailed_at` / `email_attempts`). Only signed-up users (not sample profiles) with `emailNotifications` on get email. Needs `APP_URL` (public web address for links).
- Two-person (4-eyes) approvals, actual OCR and live grant workflows are not enabled yet. One administrator approves everything; the UI says so. Token revocation: a role change, ban or sign-out takes effect when the access token expires (Supabase default 1 hour).
- Uploads (profile photos, identity documents, proposal files) are written to the API server's disk in `UPLOAD_DIR` (default `artifacts/api-server/uploads/`, git-ignored), with metadata in `demo_files`. The server checks real file types from the bytes, re-encodes images with sharp (strips EXIF/GPS, caps pixels), refuses PDFs with scripts/attachments and macro Word files, caps files at 10 MB, and serves them owner-only with a sandbox CSP. With `CLAMAV_SOCKET` (or `CLAMAV_HOST`) set, every upload is first streamed to a ClamAV daemon (`lib/virusScan.ts`); flagged files are refused, and uploads fail closed (503) while the scanner is down unless `CLAMAV_FAIL_OPEN=1`. That disk is not durable on Replit; production runs on the EU VPS (https://access.futurenestfund.org, see `server.md` and `docs/DEPLOY.md`) with `UPLOAD_DIR=/var/lib/futurenestfund/uploads`, which survives deploys and is backed up nightly. The UI asks users to upload sample documents only.
- **Error monitoring** (`api-server/src/lib/monitoring.ts`, `grant-platform/src/lib/monitoring.ts`): random request id per request (`X-Request-Id`, every log line); a 500 shows only a short reference; browser crashes go to `POST /api/client-errors` (mounted before the sign-in check, 20/min per IP). Optional `SENTRY_DSN` forwards to Sentry/GlitchTip through the envelope API (no SDK), without user, cookies, headers, IP or query strings, and with emails, tokens, secrets and long numbers scrubbed. Admin Settings has a "Send test errors" button.
- No payment processor or card network is connected. Any card, confidence score, grant/application, chart or document shown is sample data.
- Do not describe a demonstration confidence score as real OCR or the preview role switch as sign-in.
